# Week 11 — 비동기 처리

> **결론:** 보호 작업을 만들면 작업 번호를 바로 돌려주고(38.7초 → 0.04초 이내), 처리는 뒤에서 한 장씩 순서대로 한다. AI 서버가 잠깐 꺼지면 다시 시도하고, 백엔드가 도중에 꺼져도 다시 켜면 이어서 끝낸다.

## 목표
AI 처리(사진 1장 약 40초) 동안 사용자가 응답을 기다리지 않게 한다.

## 핵심 개념
- **동기와 비동기:** 동기는 일이 끝날 때까지 기다린다. 비동기는 접수만 하고 바로 돌아온 뒤, 결과를 나중에 확인한다.
- **작업자 1개:** AI 서버가 한 번에 한 장만 처리하므로, 뒤에서 일하는 스레드도 1개만 둔다. 나머지 작업은 줄을 선다.
- **재시도:** 다시 하면 나아질 수 있는 실패(연결 안 됨)에만 한다. 얼굴이 없는 사진은 다시 해도 같다. 응답이 늦은 경우도 AI 서버가 아직 계산 중일 수 있어 다시 보내지 않는다.

## 구성
| 파일 | 바뀐 것 |
|---|---|
| `job/JobWorker` (새 파일) | 줄, 순서대로 처리, 재시도(최대 3번, 5초·10초 쉼), 다시 켰을 때 이어서 하기 |
| `job/ProtectionJobService` | AI를 직접 부르지 않고, QUEUED로 저장한 뒤 줄에 세우고 바로 돌아옴 |
| `job/JobStatus`, `ProtectionJob` | QUEUED 상태, 시도 횟수, 시작 시각 추가 |
| `ai/AiClient` | 실패를 "다시 시도할 만한 것"과 아닌 것으로 구분 |
| `schema.sql` | Week 10에 만든 DB 표를 고침 |

상태: `QUEUED` → `PROCESSING` → `DONE` / `FAILED`

### 트러블슈팅
| 문제 | 원인 | 해결 |
|---|---|---|
| 기존 DB에 QUEUED를 저장할 수 없음 (미리 발견) | 상태 칸이 정해진 값만 받는 ENUM | 글자(VARCHAR)로 바꾸고 DB 복사본에서 먼저 확인 |
| 자동 테스트가 실제 DB의 작업을 다시 처리할 위험 | 테스트도 서버를 켜므로 이어서 하기가 실행됨 | 테스트는 메모리 DB와 별도 폴더 사용 |

## 결과
| 시험 | 결과 |
|---|---|
| 사진 3장 연속 요청 | 0.005 ~ 0.038초에 응답, 순서대로 모두 DONE |
| 처리 중 백엔드 강제 종료 | 다시 켜자 남은 2개를 이어서 DONE |
| AI 서버 계속 꺼짐 | 3번 시도, 16초 뒤 FAILED |
| AI 서버가 중간에 켜짐 | 2 ~ 3번째 시도에 DONE |
| 얼굴 없는 사진 | 재시도 없이 FAILED |
| 보호 결과 | Week 9 결과와 바이트까지 같음 (a_1) |

자동 테스트 9개 통과. 전체 기록: `results/week11/async_test.txt`

## Redis를 쓰지 않은 이유
서버가 1대이고 작업 기록이 이미 DB에 있어서 필요하지 않다. 백엔드를 여러 대로 늘리면 같은 작업을 두 번 처리할 수 있으므로 그때 필요하다.

## 한계
- 한 장씩 처리하므로 10명이 동시에 요청하면 마지막 사람은 약 6분 기다린다.
- 줄 길이에 제한이 없다.
- 끝났는지 사용자가 직접 조회해야 한다(알림 없음).
- 강제 종료 때 처리 중이던 사진은 AI 서버가 처음부터 다시 계산한다.

## 깨달은 점
- 비동기로 바꾼다고 처리가 빨라지지는 않는다. 기다리는 방식만 바뀐다.
- 실패라고 다 다시 시도하면 안 된다. 다시 해서 나아질 실패인지 구분해야 한다.
- 뒤에서 하는 일은 서버가 꺼지면 사라진다. DB에 상태를 남겨야 이어서 할 수 있다.
